# MCP operations

## Release

Use Bun to install, build, and test; ship the CLI under Node. Resolve dependency
updates with `bun update --latest --minimum-release-age=259200`. Commit `bun.lock`
with `package.json`. After upgrading Biome run `bunx biome migrate --write`.

Bump the package version for a release and run:

```sh
bun install --frozen-lockfile
bun run build
bun run typecheck
bun run lint
bun run format:check
bun test
```

Merge the reviewed change through a GitHub PR. Tag that main-branch commit with
`v<package-version>` and push the tag. `.github/workflows/release.yml` tests the
commit, publishes to npm with GitHub OIDC provenance, then creates the GitHub
release. Publishing uses npm trusted publishing; no local npm token or OTP is
needed for this path. Check the actual workflow outcome, registry version, and
installed artifact's `--version` before declaring currency.

## Server icon

`createMcpServer()` supplies `serverInfo.icons` for both stdio and HTTP. The
repository ships an original purple rounded square with a white checkmark,
generated by `scripts/generate-mcp-icons.py`, in 128×128 and 64×64 PNG sizes.
Regenerate the embedded defaults with `python3 scripts/generate-mcp-icons.py`,
then format `src/mcp/default-icons.ts` with Biome. No Omni artwork ships in the
repository or npm package.

Set `OMNIFOCUS_MCP_ICON_PNG` to a readable local PNG path to override the default
with one embedded data URI and dimensions derived from its IHDR. The listener
reads the image once at startup; restart it to change artwork. Unreadable files,
invalid PNG headers, or zero dimensions fail startup. Clients need no separate
image request through Cloudflare Access. Clients may ignore or cache this metadata;
reconnecting may be needed before an icon changes. No favicon route or image
exception bypasses Access. Icons are standardized in the
[2025-11-25 schema](https://github.com/modelcontextprotocol/specification/blob/main/schema/2025-11-25/schema.ts).
The SDK also emits this optional metadata when negotiating 2025-06-18; older
clients may ignore it.

For launchd deployments, set `OMNIFOCUS_MCP_ICON_PNG` to the absolute PNG path in
the live agent's `EnvironmentVariables`. Reload the agent with bootout/bootstrap
to apply plist changes; `kickstart` alone uses the cached configuration. Once the
variable is loaded, artifact-only upgrades can use a single kickstart per agent.
Verify the override by comparing decoded initialize icon bytes with the local
PNG, then verify a real read through an approved listener. An authenticated
public listener must continue rejecting requests without credentials.

## Capability and authentication boundaries

Full mode is the default (30 tools). `--mode read-only` registers 17 tools and
excludes all twelve create/update/delete tools and `get_perspective_tasks`, which
changes the user's front window. The same allowlist filters `search_tools`.
Excluded tools are unregistered and direct calls fail. A listener owns its mode;
caller claims do not select a mode. Issue a credential for a separate read-only
listener when a principal needs fewer capabilities.

HTTP JWT enforcement is enabled by configuring both `--access-team-domain` and
`--access-audience` (or `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUDIENCE`). Partial
configuration fails startup. Authenticated HTTP requires the
`Cf-Access-Jwt-Assertion` header even on localhost; neither Host nor a service-token
identity header bypasses it. The origin verifies RS256 signature, exact issuer,
application audience, required expiry, and not-before when present. JOSE obtains
and caches rotating keys from the configured team's `/cdn-cgi/access/certs`.
Key-fetch and verification failures reject the request. Do not log assertion or
service-token values.

Service-token clients send `CF-Access-Client-Id` and `CF-Access-Client-Secret` to
Cloudflare. Access validates those credentials and supplies the signed assertion
to the origin. The origin never treats client-supplied identity as authorization.
Interactive clients use the Access application's Managed OAuth configuration.

HTTP request capacity and OmniFocus execution capacity are separate. Disconnects
free HTTP capacity; an OmniFocus execution retains its slot until its promise
settles. The limit applies across all requests to that listener.

Each listener admits OmniFocus operations through one gate. A call that times
out leaves its Apple event queued inside OmniFocus, where it holds a thread
until OmniFocus reaches it. After a timeout the gate therefore answers
`unresponsive` (503) for 30 seconds without sending anything, then admits one
call at a time. An answer from OmniFocus, including an error such as
`not_found`, reopens the gate. A timeout holds it for another 30 seconds. A
failure that never reached OmniFocus, such as rejected arguments or a consent
error, leaves it admitting one call at a time. A timeout from a call sent before
the gate last held or reopened is ignored. Restarting a listener clears its
gate. One slow call that times out holds every caller for those 30 seconds.

Every script also carries the moment its caller stops waiting and does nothing
when OmniFocus reaches it later, so a queued call cannot change the database
after its caller was told it timed out. A script OmniFocus had already started
runs to completion.

Listeners log to stderr with a UTC timestamp: one startup line naming the CLI
version, endpoint, and mode; `bridge=first-answer` once, when OmniFocus answers
the first call after startup; one line per failed tool call (`tool`, `error`,
`status`, `changes`, `ms`); and `bridge=unresponsive` / `bridge=responding` when
the gate holds and reopens. Lines never include arguments or error detail.
Successful calls are otherwise not logged. The startup and first-answer lines
confirm a restart on a listener that the operator cannot authenticate to.

## Mac Mini public deployment example

The files in [deployment/](deployment/) are templates. Replace the example
hostname `omnifocus.example.com`, team domain placeholder
`example.cloudflareaccess.com`, and `YOUR_ACCESS_AUDIENCE` with your Cloudflare
Access configuration. Replace `/Users/you` with your home directory and choose
your own `com.example.` labels and bundle identifier, keeping them consistent
across the plists. Plist paths must be absolute; launchd does not expand `$HOME`
or `~`. The paths and pinned versions illustrate one installation layout.

The private fallback is independent: `com.example.omnifocus-mcp` listens on
127.0.0.1:3939. Its example Tailscale hostname is
`mac-mini.example-tailnet.ts.net`, with Serve 8443 → 127.0.0.1:3939. Use your
own machine's hostname. Preserve the fallback's plist, absolute Node binary path,
signed launcher identity, and Serve configuration during upgrades. Both listeners
use the same launcher bundle and the pinned official Node v26.13.0 runtime.

The public service is `com.example.omnifocus-mcp-public`, bound only to
127.0.0.1:3940, allowing Host `omnifocus.example.com`. Its configured issuer is
`https://example.cloudflareaccess.com`, using the team domain placeholder above.
The Access application owner supplies the application audience. Replace
`YOUR_ACCESS_AUDIENCE` in both public LaunchAgent templates with that value.
Changing the audience does not require rebuilding the package.

Install a pinned npm artifact in:

```text
~/Library/Application Support/omnifocus-mcp-public/releases/2.11.0/
```

Use `npm install --prefix <release-directory> --ignore-scripts --save-exact
@stephendolan/omnifocus-cli@2.11.0`. The signed launcher starts that artifact's
`dist/cli.js` under an absolute, versioned Node path. The existing global
installation remains the fallback's CLI artifact. Use the launcher templates
linked below to prepare the agents in `~/Library/LaunchAgents/`. Keep the public
installation directory mode 700. Reload only the public service when changing
its audience or mode.

For an upgrade with fixed LaunchAgent paths, install the pinned npm artifact into
the public agent's existing prefix (which can retain an older version in its
directory name). Update the fallback's global package from that same npm artifact,
preserving unrelated global packages. Keep both installed plists byte for byte,
including their launcher, Node, CLI, and icon paths. The external Node runtime
does not own the listeners' Automation grant; the signed launcher bundle does.
Restart each listener once after updating its artifact:

```sh
launchctl kickstart -k gui/$(id -u)/com.example.omnifocus-mcp-public
launchctl kickstart -k gui/$(id -u)/com.example.omnifocus-mcp
```

Verify changed PIDs and launch times, then initialize each localhost endpoint and
check version `2.11.0`, `serverInfo.icons`, and its tool list. Full mode has 30 tools; read-only has 17.
The public endpoint requires a real Access assertion even on localhost.

`folder create <name>` and the full-mode `create_folder` tool return the folder
fields plus `alreadyExisted`. They match exact top-level names, including dropped
folders, and reuse a match without changing it. Nested names do not match.

Prepare `com.example.omnifocus-cloudflared` from the separate template,
substituting `__TOKEN_DIRECTORY__` with `~/.cloudflared` expanded to an absolute
path. Keep that directory mode 700 and the agent unloaded until the securely
transferred token is present at `~/.cloudflared/omnifocus-tunnel.token`, mode 600.
The template also waits for the token path before starting if launchd loads it
at login. Never put the token in a plist, command argument, repository, or chat.
Do not create a dummy token. The remotely managed tunnel routes the host to
`http://127.0.0.1:3940`, with a final 404 ingress. The external endpoint is
`https://omnifocus.example.com/mcp`.

For encrypted token handoff, generate a one-time RSA-4096 private key at
`~/.cloudflared/transfer-key.pem`, mode 600. Share only its public key. Use
RSA-OAEP with SHA-256 and MGF1-SHA-256, transfer the ciphertext as base64, and
decrypt directly into the mode-600 token file. Verify cloudflared can read the
token before removing the transfer private key.

## Perspective rule archives

`get_perspective_rules {"idOrName":"Example"}` reads an existing custom
perspective by exact name or stable Omni Automation identifier. Duplicate names
require an identifier. Its JSON tool content is
`{"id":"PERSPECTIVE_ID","name":"Example","definition":{...}}`.
`update_perspective_rules {"idOrName":"PERSPECTIVE_ID","definition":{...}}`
replaces the complete archive and returns the same shape with the actual saved
definition. Reading is available in both modes; updating requires full mode.
Neither operation needs a window or switches the current perspective.

A definition has exactly these fields:

```json
{
  "archivedFilterRules": [
    {"actionAvailability":"available"},
    {"aggregateType":"none","aggregateRules":[{"actionIsProject":true}]}
  ],
  "archivedTopLevelFilterAggregation": "all"
}
```

`archivedFilterRules` is an array of nonempty JSON rule objects, including nested
`aggregateType` / `aggregateRules` groups. Aggregations are `all`, `any`, or
`none`; the top-level aggregation also accepts `null` as exposed by OmniFocus.
Unknown rule fields and JSON values are preserved for archive fidelity. The JSON
key `__proto__` is rejected because the validator would discard it. Validation
checks JSON and group structure, not an exhaustive list of OmniFocus predicates.
An empty array clears all filters. Built-in perspectives have no editable rules
and fail explicitly. These operations cannot create a perspective.

The [Omni Automation rule archive API](https://omni-automation.com/omnifocus/perspective.html)
exposes the filter tree and aggregation. Grouping, sorting, hierarchy, and row
layout belong to the exported perspective plist, not this rule archive. This API
does not expose setters for those presentation options; rule updates preserve
them. Do not add export-plist fields to the definition.

Input validation happens before Apple events. Updates snapshot both properties,
write them in one synchronous Omni Automation evaluation, and compare the complete
readback with the requested definition, ignoring object key order. Setter errors
or normalization trigger restoration and verification of the original archive.
Restoration errors are reported explicitly; the API provides no transaction primitive
and cannot guarantee recovery if OmniFocus also refuses restoration or the bridge
terminates during a write. A transport failure alone does not establish write outcome;
read the definition before retrying.

CLI equivalents:

```sh
of perspective get-rules Example > perspective.json
jq '.definition' perspective.json > definition.json
of perspective update-rules Example --file definition.json
# Or pipe the definition to --file -
```

Verify an authorized round trip over the existing fallback HTTP listener: save
`get_perspective_rules`, call `update_perspective_rules` with its exact `definition`
and returned `id`, read again, and compare parsed definitions (including every
unknown field). Check `result.isError` as well as HTTP status. Keep actual database
values and acceptance evidence outside this operations document.

## Health and macOS automation

An MCP initialize or tools/list response proves transport availability. A tool
response with HTTP 200 can still contain `result.isError: true`. Health requires
a successful real read, such as `get_project_stats`, with valid parsed tool content.
`get_inbox_count` traverses and serializes the inbox; it is not a cheap liveness
probe. Avoid `get_perspective_tasks` for health because it switches the user's view.

Agent contexts (BB threads and shells under unapproved ancestors) must NEVER
probe OmniFocus with `node dist/cli.js`, `osascript`, or JXA. Live reads route
through the existing localhost MCP listeners. If a listener read times out,
stop live calls and leave dialogs and the permission queue untouched. Do not
interact with a locked session, reset grants, or relaunch OmniFocus unattended.

macOS attributes child Apple Events to a responsible ancestor. An absolute Node
path does not guarantee attribution to that Node binary: a BB thread can inherit
the BB daemon's unapproved TCC identity. Consent dialogs from unapproved contexts
can block OmniFocus script access. Retain each listener's approved runtime path
when staging a launcher cutover, then use the signed bundle as described below.
Do not run mise commands during staging or deployment: they can prune installed
runtimes.

The only sanctioned direct check in an agent context is `of doctor` without
`--request-consent`. It calls `AEDeterminePermissionToAutomateTarget` for
`com.omnigroup.OmniFocus4`, with wildcard event class/ID and
`askUserIfNeeded=false`; it sends no Apple event and cannot prompt. The same
preflight guards every operation before `evaluateJavascript`. Status -1744
returns `automation_consent_required`; -1743 returns `automation_denied`. Both
have `statusCode: 403`. Other nonzero statuses return
`automation_preflight_failed` with `statusCode: 503`. CLI errors exit 1 and
include `osStatus` and `execPath`; MCP returns the typed JSON with
`isError: true`. An unapproved BB shell can return -600 even while reads through
the approved listeners succeed. Do not infer that OmniFocus is stopped from that
status alone. `execPath` names the CLI runtime, not necessarily the ancestor TCC
considers responsible.

`of doctor --request-consent` is the only path that sets `askUserIfNeeded=true`.
It is reserved for attended setup under the intended signed launcher identity;
never execute it directly from a BB shell. Tests use bridge and executable
mocks, never live Apple events or real `osascript`.

A successful signal command does not prove a service restarted. Verify its PID
and launch time before calling a check post-restart. TCC enables
`EnablePressuredExit`; the Mac's `launchd.plist(5)` manual documents that these
jobs can handle SIGTERM without exiting. Preserve this distinction when a
permission-dialog wait survives the signal.

Validate the public origin locally with missing and forged assertions (401), then
with a real Access-issued assertion for the exact configured audience. Use a
private token file and a test client that never prints its contents. Repeat real
reads through Tailscale 8443 and compare the original plist and Serve configuration
with the saved inventory. Valid local test signatures prove verifier behavior;
they do not prove the real Access application or tunnel configuration.

## Signed launcher and external runtime

Both listeners start the same signed background app, built from
[launcher/](deployment/launcher/). The templates use bundle identifier
`com.example.omnifocus-mcp`. The app declares an Automation usage description
and carries `com.apple.security.automation.apple-events`. Its bundle version,
the external Node version, and the CLI package version are independent.
Build to a fresh absolute output path with:

```sh
SIGNING_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
  docs/deployment/launcher/build.sh "/absolute/output/OmniFocus MCP.app"
```

Set `SIGNING_IDENTITY` to your Developer ID Application identity or certificate
fingerprint; the example above is a placeholder. The build requires this input
and uses hardened runtime and an Apple timestamp. Verify with `codesign -d -r-`
and `codesign --verify --strict`. The launcher uses `posix_spawn`, forwards SIGTERM,
SIGINT, and SIGHUP, and exits with the child's exit code (128 + signal for a
signal termination). Node and JavaScript remain outside the bundle. Keep the
bundle identifier and signing identity stable across runtime upgrades. The
verified launch chain is:

```text
GUI launchd → signed launcher app → external Node → installed CLI → osascript
```

Both listeners share the bundle's Automation grant. A second listener or a Node
version change does not need another consent request while that grant and bundle
identity remain intact. Verify TCC responsibility in logs rather than assuming
that a signed executable establishes it: a direct invocation from a BB shell can
still inherit BB's ancestry.

The official `node-v26.13.0-darwin-arm64.tar.gz` from
[nodejs.org](https://nodejs.org/dist/v26.13.0/) is checked against that release's
`SHASUMS256.txt` before extraction to
`~/Library/Application Support/omnifocus-mcp/runtime/node-v26.13.0/`. Its SHA-256
is `d38bd5e5a2ddce6bbb5ce45e46e208337da4d51fffe611e567fd32073d6439f6`.
Verify the unpacked `bin/node` with `codesign --verify`; do not re-sign Node.

Example listener definitions are provided at
[com.example.omnifocus-mcp.staged.plist](deployment/com.example.omnifocus-mcp.staged.plist)
and
[com.example.omnifocus-mcp-public.staged.plist](deployment/com.example.omnifocus-mcp-public.staged.plist).
Their arguments prepend the launcher and staged Node to the existing CLI entry
and listener arguments. They add `AssociatedBundleIdentifiers` for the launcher.
These are parameterized templates, **not copies of installed LaunchAgents**.
Derive replacements from the current live plists and use the templates for
structure only. Replace the original Node entry with the launcher followed by
the external Node entry, leaving the CLI path and every subsequent argument
unchanged. If a live plist has a separate `Program` key, update it consistently.
Preserve the entire environment, including `OMNIFOCUS_MCP_ICON_PNG` on both
listeners, and associate both jobs with the same actual bundle identifier.
Compare the replacements locally, redact Access values in any report, and run
`plutil -lint` before installation. Use bootout/bootstrap to load changed plists;
kickstart alone retains launchd's cached configuration. Do not change the tunnel
or Tailscale Serve configuration.

### One attended consent grant

Before the initial cutover, the user must unlock the Mac and dismiss any stale
consent dialogs. A pending dialog can hold TCC's prompt slot. Switch the public
listener first and confirm unauthenticated initialize returns 401 before making
an OmniFocus tool call.

For the single attended consent request, prepare a one-shot LaunchAgent in the
GUI domain with a unique label, `RunAtLoad=true`, `KeepAlive=false`, the same
`AssociatedBundleIdentifiers`, and absolute `ProgramArguments`:

```text
[<LAUNCHER_EXECUTABLE>, <NODE_BINARY>, <CLI_DIST>, doctor, --request-consent]
```

Start it through GUI launchd without a shell in the child chain. The user clicks
Allow in person. Never script the click. The installed doctor has a 30-second
inner timeout; a longer outer wait cannot extend it. Stop on failure or timeout
and do not repeat the prompting command automatically.

Require doctor to return `granted` with OSStatus 0 and the one-shot job to exit 0.
Correlate `log show` entries from subsystem `com.apple.TCC` with the request time
and process IDs. `AttributionChain` must name the actual launcher bundle as
**responsible**, and the grant must target OmniFocus. Mere presence of the
bundle somewhere in the chain is insufficient. Then verify a real public read
through an authenticated client. Keep its credentials on that client's host;
they need not be copied to the Mini. Retain the exited job's output as evidence.

### Runtime acceptance and listener verification

Download a different official Node version from nodejs.org, compare its tarball
with that release's `SHASUMS256.txt`, and verify the extracted Node signature
without re-signing it. Stage it alongside the pinned runtime. Change only the
public plist's Node argument, bootout/bootstrap, and verify a real
`get_project_stats` read with no prompt. Restore the pinned path, restart once,
and verify another real read. Acceptance covers official Node v26.13.0 and
v26.12.0 while retaining the same launcher bundle.

Switch the fallback to the same launcher and pinned runtime, initialize on
3939, compare decoded icon bytes, and verify a real read through that listener.
Do not request consent again. If a prompt appears, stop. Public initialization
without credentials must still return 401; authenticated initialization supplies
the CLI version and icons. Check the live Node child executable and its
`--version` as well as the new listener startup log. The startup log prints the
CLI version, endpoint, and mode, not the Node version. Verify changed PIDs and
launch times after each planned restart.

### Recovery after a timeout

Stop further reads and restarts, including a planned runtime restoration. Leave
OmniFocus, dialogs, and TCC state untouched. Preserve the client deadline,
startup log, process IDs, and read-only TCC attribution evidence. HTTP 200 alone
is not success; parse the tool result and reject `isError: true`.

A timeout returns `code: "timeout"`; the calls that follow within 30 seconds
return `code: "unresponsive"` without reaching OmniFocus. The listener log
records both, with `bridge=unresponsive` at the moment the hold began. Each
`changes` value states what a failed call did: a write that timed out is
`unknown` and needs a read-back once reads work again, while `unresponsive`,
`expired`, and every failed read are `none`.

A first read after restart can exceed the client's deadline, but that does not
establish the cause. An HTTP disconnect also does not prove the server-side
operation finished. After a fresh user steer authorizes recovery, make only the
bounded retry they requested. A successful real read verifies recovery; another
timeout stops the sequence again. Do not add a consent request or restart as an
automatic recovery step. Use `of doctor` without `--request-consent` for a
preflight-only check from an agent context; it is not a substitute for a real
listener read.
